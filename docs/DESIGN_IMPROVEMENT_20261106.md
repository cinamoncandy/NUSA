## 3. 누사포지 L1 구조 개선 (제안 3)
L1 = 워크플로 실패를 믿을 수 있는 증거로 분류해 자율 코딩을 시작하는 경로. 지금 상태는 PARTIAL이다.

1. **L1 완료의 정의를 측정 가능하게 적는다.** 지금은 "양성 증명서가 있다" 정도로 흩어져 있다. 다음을 모두 만족할 때만 L1 COMPLETE로 쓴다: (a) 보호된 main 푸시에서 나온 진짜 증명서, (b) 소비 검증기의 전 항목 통과, (c) 승인 `CODE_ACTIONABLE`, (d) 수리 대상 한 파일의 초안 PR 한 건, (e) 그 PR이 사람(비작성자) 검토와 Audit를 거쳐 병합되고 CI가 다시 초록이 됨. 이번 카나리는 (a)와 일부 (b)만 겨냥한다. 이를 문서의 표로 고정한다. (SAFE, 기록)
2. **자율개발 일시중지 스위치를 둔다.** 지금은 자율 코딩만 멈추는 전용 스위치가 없다(전체 릴리스 동결 `NUSA_GLOBAL_RELEASE_FREEZE`는 Audit·Release까지 막으므로 카나리 중에는 쓸 수 없다). 읽기 쉬운 단일 플래그로 "자율 코딩 시작 금지"를 둔다. 권한을 줄이는 방향이다. (OWNER, 독립 검토 필요)
3. **연결되지 않은 제어 평면 항목 33개를 세 부류로 정리한다.** `unwiredControlPlaneDebt.ts`의 목록을 (a) `CODE_ACTIONABLE` 경로에 필요한 것, (b) 선언된 설계상 아직 연결 안 한 것(작업 풀, 백프레셔), (c) 사용 계획이 없는 것으로 나누고 (c)는 삭제를 제안한다. 목록은 "측정이지 판단이 아니다"라고 적혀 있으니, 줄이는 diff가 곧 기록이다. (SAFE)
4. **자율 코딩의 종점을 하나로 고정한다.** 게시기가 초안만 만들고(`draft: true`, 테스트 보호) 초안 해제는 사람/Audit가 한다는 불변식은 좋다. 같은 PR 생성 경로가 여러 곳(`autopilot-codex-coding.yml`은 `--draft` 없이 `gh pr create`, 현재 `disabled_manually`)에 있는 것은 위험이다. 비활성 워크플로를 삭제하거나 `--draft`를 강제한다. (OWNER, 워크플로 권한)
5. **빨간 main 처리 규칙을 문서와 코드에 한 번에 적는다.** 현재 Release가 실패한 main CI를 자동으로 최대 3회 재실행하는 사실이 계획서에만 있다. 이를 운영 문서의 한 절로 올린다. (SAFE, 기록)

## 4. 누사 전체 구조 개선
### 4-1. 같은 계산을 여러 곳에서 따로 구현하는 문제 (가장 중요)
이번 주 사고가 모두 여기서 나왔다.
- **체결 재생(replay)** 이 네 곳에 따로 있다: 원장(`paperTradingExecutionLoop`, 수량을 소수 8자리로 반올림), 위험 게이트(`cloudPaperCanonicalRiskGateway.ts`, 원시 부동소수점이었다 → #2999), 오늘 실현손익 표시(`paperTodayRealized.ts`), 손실 분류(`paperLossAttribution.ts` → #3003). 위험 게이트의 불일치가 7,379건의 매수 차단을 일으켰다.
- 제안: **체결 재생과 수량 반올림을 한 모듈로 모으고** 네 곳이 그것을 쓰게 한다. 원장과 위험 게이트의 일치를 한 속성 테스트(무작위 이력)로 계속 검증한다(#2999의 11개 테스트가 출발점). 위험 게이트는 핀 모듈이라 정식 재인정 경로가 필요하다. (OWNER, 가장 큰 이득)

### 4-2. 생성 파일 `CURRENT_TRUTH.md`가 병합마다 CI를 깨뜨린다
오늘 확인한 사실: #2973(main 합류 뒤 `coverage-core-1`의 `aipos-current-truth` 실패, 로그로 확인), 같은 조치(main 합류 + 파일 재생성)를 #2973 뒤에 #2998, #3003, #3004와 롤링 묶음 브랜치 3개에 반복했다. 원인은 작업 지시서 개수가 main 병합마다 바뀌는 것이다(#2998은 로그에 원인 줄이 없어 같은 원인으로 **추정**).
- 제안: 이 파일을 커밋하지 않고 CI에서만 생성하거나, 개수를 파일에서 빼서 병합 충돌과 노후화를 없앤다. 기록이 바뀌면 사람이 다시 만드는 규칙이 반복 비용이다. (SAFE, 기록 도구)

### 4-3. 병합 흐름의 마찰
- Audit는 PR의 기준 main이 지금 main과 같을 때만 통과시키고(우리가 #2973에서 겪음), 보호 규칙도 "병합 전 최신 main 필수"다. 병합이 잦으면 PR마다 main을 다시 합치고 CI를 다시 돌려야 한다. 병합 대기열이 없다(오너 캡처로 확인).
- 제안: 병합 대기열이나 "자동 갱신" 방식을 오너가 검토한다. 단 `nusa/release-authorized` 필수 체크와 호환되는지 먼저 확인해야 한다. (OWNER, 설정)

### 4-4. 10-28 평가에서 아직 열린 항목 (확인된 것만)
- 위험 신원이 `ACCOUNT_ID = "paper-default"`로 고정(핀 파일, 재인정 필요). 세션 낙폭 고점이 메모리에만 있고 재시작에 초기화(OWNER).
- 학습 성과 0: 구성 192개, 홀드아웃 통과 0은 10-28 값이다. 현재 값은 다른 세션의 읽기 전용 점검 기준 `holdoutPasses=0`. 영가설 비교(보유 유지, 무작위 진입)와 전략 다양성은 아직 없다(SAFE, 그림자 계산).
- 테스트가 소스 문자열을 단언하는 비중이 높다(10-28: 1,315개 중 383개가 `readFileSync`). 안전 단언은 대체 테스트가 통과하기 전에는 지우지 않는다(SAFE).
- 호스트: 1 vCPU, 954 MB, 백업 2시간(상태 DB 분리 작업 미완)은 현재 상태를 이번에 다시 측정하지 않았다(UNVERIFIED).
