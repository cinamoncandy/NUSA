# Autopilot 가벼운 작업 우선 설계 (크기 상한)

상태: **설계 제안(기본값 적용)**. 코드·설정·권한 변경 없음 (`authority_impact: none`). 이 상한은 오토파일럿이 하는 일을 **줄이기만** 하며
어떤 권한도 늘리지 않습니다. 구현은 이 문서가 승인된 뒤 별도 작업지시서로 진행합니다.

## 1. 역할 분담과 목적 (소유자 2026-10-12 채팅)
- 이 보조 Claude는 보조 역할이고, **오토파일럿은 가벼운 작업을 우선**합니다. 큰 변경은 오토파일럿이 아니라 소유자나 보조 Claude에게 갑니다.
- 가벼운 변경은 검토·되돌리기가 쉽고, CI·Audit 한 번으로 끝나기 쉬우며, 소유자 코딩과 충돌할 가능성이 작습니다.

## 2. 지금 상태 (코드에서 확인한 범위)
- 오토파일럿은 대부분 **반응형**입니다. CI 실패, PR 변경 같은 이벤트가 오면 그 건을 처리하며, 대기열에서 무거운 것과 가벼운 것을 고르는 구조가 아닙니다.
- 코딩 제안에는 이미 바이트 한도가 있습니다(제안 전체 24KB, 수정 한 건의 텍스트 8KB). 파일 수와 변경 줄 수의 한도는 없습니다.
- 작업 우선순위 함수(`opportunityPlanner`, `effortCost` 포함)는 있지만 실제 호출처가 없습니다(연결 안 된 함수 목록). 지금은 "가벼운 것부터 고르기"가
  동작하지 않습니다.

## 3. 기본값
| 항목 | 기본값 |
|---|---|
| 한 번에 바꾸는 파일 수 | 3개 이하 |
| 한 번에 바꾸는 줄 수(추가+삭제) | 150줄 이하 |
| 설정 이름 | `NUSA_AUTOPILOT_MAX_CHANGED_FILES`, `NUSA_AUTOPILOT_MAX_CHANGED_LINES` |

소유자가 값을 조정할 수 있습니다. 값은 **배포 설정에서만** 바뀝니다. 오토파일럿이나 AI가 스스로 올릴 수 없고, 요청 본문으로 덮어쓸 수 없습니다.

## 4. 어디서 어떻게 막는가 (새 구조 없음)
1. **제안 단계**: Worker의 코딩 제안(`/coding/propose`)이 패치를 돌려주기 전에, 패치(unified diff)에서 바뀐 파일 수와 변경 줄 수를 **결정적으로** 센다.
   - 파일 수는 diff 헤더에서, 줄 수는 `+`/`-`로 시작하는 줄(헤더 제외)에서 센다.
   - 한도를 넘으면 사유 코드 `CODING_PROPOSAL_TOO_LARGE`로 거절한다. 패치는 게시(publish) 경로로 넘어가지 않는다.
2. **게시 직전 재확인**: 게시(`/coding/publish`)에서도 검증된 파일 목록으로 같은 상한을 다시 확인한다(제안과 게시 사이의 변조·누락 방어).
3. **분류**: `CODING_PROPOSAL_TOO_LARGE`는 기존 제안 거절 계열로 분류한다(`PROPOSAL_REJECTED`).
   - 기존 재생성 장치와 예산(최대 3회)을 그대로 쓴다. 재생성 때 짧은 피드백(`proposalFeedback`, 512바이트 한도 안)으로 "범위를 줄여라"를 전달한다.
   - 예산을 다 쓰면 기존 규칙대로 `FAILED_TO_REMEDIATE`와 증거가 남고, **오토파일럿은 더 크게 시도하지 않는다.** 이 건은 소유자 또는 보조 Claude가 처리할 일이다.
4. **판단이 불확실하면 닫힘**: diff를 해석할 수 없거나 설정값이 없거나 숫자가 아니면 "너무 큼"으로 취급한다.

## 5. 경계와 다른 장치와의 관계
- `VALID_NO_ACTION`과 구별됩니다. 너무 커서 거절된 건은 "할 일 없음"이 아니라 "오토파일럿이 할 일이 아님"이며, 완료 영수증에서도 생산으로 세지 않습니다.
- 소유자 활동 게이트(#2641)와 같은 입구를 쓰지만 **독립적인 두 검사**입니다. 하나는 "지금 시작해도 되나", 다른 하나는 "이 크기를 맡아도 되나"입니다.
- CI, 결정적 Audit, 릴리스 봇의 병합, 배포는 건드리지 않습니다.

## 6. 하지 않는 것 (이번 설계 범위 밖)
- **대기열 정렬**: 작업이 여러 개 쌓일 때 가벼운 것부터 고르는 순서 정하기는 하지 않습니다. 오토파일럿이 반응형이라 대기열이 거의 없고,
  지금 `opportunityPlanner`를 연결하면 연결 안 된 함수만 늘고 효과가 작습니다. 실제로 대기열이 생기면 별도 작업으로 다룹니다.
- **무거운 작업의 자동 이관**: 크기 초과 건을 소유자·보조 Claude에게 넘기는 자동 라우팅은 없습니다. 거절 증거가 남고, 사람이 보고 판단합니다.

## 7. 승인 기준 (구현 시)
- 결정적 단위 테스트: 정확히 3파일/150줄은 통과하고 4파일 또는 151줄은 거절, 헤더 줄은 세지 않음, 파일 이름 변경·삭제·바이너리·빈 diff 처리,
  해석 불가 diff는 거절, 설정 누락·비숫자·0·음수는 닫힘.
- 요청 본문에 한도를 넣어도 무시된다는 테스트, 게시 단계 재확인 테스트, `CODING_PROPOSAL_TOO_LARGE` 분류와 재시도 예산 소모 테스트.
- 거절 시 게시 경로·유료 호출이 일어나지 않는다는 테스트, 배포 설정(값 존재) 테스트.
- 연결 안 된 함수 목록에 새 항목이 생기지 않음.

## 8. 열린 결정 (소유자)
1. 기본값 3파일/150줄이 맞는지(제가 정한 제안값). 문서·테스트만 바꾸는 변경은 더 느슨하게 할지도 포함.
2. 크기 초과 시 재생성(범위 축소 요청)을 시도할지, 곧바로 사람에게 넘길지(기본값은 기존 예산 안에서 재생성).

## 9. 한계 (정직한 범위)
- 설계이며 아직 구현되지 않았습니다. 지금 오토파일럿에는 파일 수·줄 수 한도가 없습니다.
- 줄 수는 크기의 대용치일 뿐 위험의 크기와 같지 않습니다. 작은 변경도 위험할 수 있고, 그 판단은 CI·Audit·릴리스 봇의 몫으로 남습니다.
