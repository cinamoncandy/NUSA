# Autopilot 가벼운 작업 우선 설계 (크기 상한)

상태: **설계(구현 PR #2643에 맞춰 갱신)**. 이 문서 자체는 코드·설정·권한 변경이 없습니다 (`authority_impact: none`). 이 상한은 오토파일럿이 하는 일을
**줄이기만** 하며 어떤 권한도 늘리지 않습니다.

## 1. 역할 분담과 목적 (소유자 2026-10-12 채팅)
- 이 보조 Claude는 보조 역할이고, **오토파일럿은 가벼운 작업을 우선**합니다. 큰 변경은 오토파일럿이 아니라 소유자나 보조 Claude에게 갑니다.
- 가벼운 변경은 검토·되돌리기가 쉽고, CI·Audit 한 번으로 끝나기 쉬우며, 소유자 코딩과 충돌할 가능성이 작습니다.

## 2. 지금 상태 (코드에서 확인한 범위)
- 오토파일럿은 대부분 **반응형**입니다. CI 실패, PR 변경 같은 이벤트가 오면 그 건을 처리하며, 대기열에서 무거운 것과 가벼운 것을 고르는 구조가 아닙니다.
- 코딩 제안에는 이미 바이트 한도가 있습니다(제안 전체 24KB, 수정 한 건의 텍스트 8KB). 파일 수와 변경 줄 수의 한도는 없습니다.
- 작업 우선순위 함수(`opportunityPlanner`, `effortCost` 포함)는 있지만 실제 호출처가 없습니다(연결 안 된 함수 목록). 지금은 "가벼운 것부터 고르기"가
  동작하지 않습니다.

## 3. 기본값 (구현 PR #2643에 맞춰 갱신)
| 항목 | 값 | 비고 |
|---|---|---|
| 한 번에 바꾸는 줄 수(추가+삭제) | **150줄 이하** | 코드 상수 `MAX_CODING_CHANGED_LINES`. 바꾸려면 리뷰를 거친 PR이 필요합니다(배포 설정이 아님). |
| 한 번에 바꾸는 파일 수 | **1개** | 새 한도를 만들지 않고 기존 규칙을 유지합니다. 제안마다 파일을 정확히 1개만 허용하고(`uniquePaths.length !== 1`이면 거절), 게시 경로도 1개만 받습니다. 처음 제안한 "3개 이하"보다 엄격합니다. |

초안은 두 값을 배포 설정(`NUSA_AUTOPILOT_MAX_CHANGED_FILES`, `NUSA_AUTOPILOT_MAX_CHANGED_LINES`)에서 읽자고 했습니다. 구현하면서 코드를 확인한 뒤
다음 두 가지를 의도적으로 바꿨습니다.
- **줄 한도를 코드 상수로**: 같은 파일의 다른 한도(바이트 한도)와 방식이 같고, 값을 올리려면 CI·Audit를 거치므로 설정값보다 엄격합니다.
  AI나 요청이 스스로 올릴 수 없다는 원칙은 그대로입니다.
- **파일 수 한도를 새로 만들지 않음**: 이미 1개로 제한되어 있어 3개 한도는 의미가 없습니다.

## 4. 어디서 어떻게 막는가 (구현된 모습)
1. **제안 검증**: 모델이 낸 패치는 `validateCodingProposal`에서, 정확한 수정(exact edit)으로 만든 패치는 `buildDeterministicCodingPatch`에서,
   변경 줄 수를 `countChangedPatchLines`로 센다(`+`/`-`로 시작하는 줄, 파일 헤더 `+++ `/`--- ` 제외).
   두 경로 모두 `/coding/propose`와 `/coding/execute`가 공유하는 코드다.
2. **한도 초과**: 기존 사유 코드 `CODING_PROPOSAL_TOO_LARGE`로 거절한다. 이 사유는 이미 `PROPOSAL_REJECTED` / `REGENERATE_PROPOSAL`로 분류되어
   기존 재시도 예산(최대 3회) 안에서 재생성된다. 새 분류나 새 경로를 만들지 않는다.
3. **예산 소진**: 기존 규칙대로 `FAILED_TO_REMEDIATE`와 증거가 남고, **오토파일럿은 더 크게 시도하지 않는다.** 그 건은 소유자 또는 보조 Claude가 처리한다.
4. **게시 경로**: 이미 파일 1개·내용 크기 한도(128KB)만 받으므로 별도 줄 수 재확인은 하지 않는다(게시 입력은 diff가 아니라 파일 내용이라 줄 수를 알 수 없다).

## 5. 경계와 다른 장치와의 관계
- `VALID_NO_ACTION`과 구별됩니다. 너무 커서 거절된 건은 "할 일 없음"이 아니라 "오토파일럿이 할 일이 아님"이며, 완료 영수증에서도 생산으로 세지 않습니다.
- 소유자 활동 게이트(#2641)와 같은 입구를 쓰지만 **독립적인 두 검사**입니다. 하나는 "지금 시작해도 되나", 다른 하나는 "이 크기를 맡아도 되나"입니다.
- CI, 결정적 Audit, 릴리스 봇의 병합, 배포는 건드리지 않습니다.

## 6. 하지 않는 것 (이번 설계 범위 밖)
- **대기열 정렬**: 작업이 여러 개 쌓일 때 가벼운 것부터 고르는 순서 정하기는 하지 않습니다. 오토파일럿이 반응형이라 대기열이 거의 없고,
  지금 `opportunityPlanner`를 연결하면 연결 안 된 함수만 늘고 효과가 작습니다. 실제로 대기열이 생기면 별도 작업으로 다룹니다.
- **무거운 작업의 자동 이관**: 크기 초과 건을 소유자·보조 Claude에게 넘기는 자동 라우팅은 없습니다. 거절 증거가 남고, 사람이 보고 판단합니다.

## 7. 승인 기준 (구현 시)
- 구현됨(#2643): 정확히 150줄은 통과하고 151줄은 거절(모델 패치와 정확한 수정 양쪽), 헤더 줄은 세지 않음, 기존 단일 파일 규칙 유지, 연결 안 된 함수 목록에 새 항목 없음.
- 아직 없음: 파일 이름 변경·삭제·바이너리 diff의 줄 수 처리 전용 테스트(현재는 `+`/`-` 줄 규칙을 그대로 따름).

## 8. 결정 현황 (소유자)
1. 기본값 → **결정됨**: 소유자가 기본값으로 구현하도록 승인했습니다. 실제 적용값은 §3(150줄, 파일 1개)입니다.
2. 크기 초과 시 → 기본값대로 **기존 예산 안에서 재생성**을 시도합니다. 곧바로 사람에게 넘기는 방식으로 바꾸고 싶으면 소유자가 알려야 합니다.

## 9. 한계 (정직한 범위)
- 구현은 #2643에 있고 병합과 Worker 배포가 되어야 실제로 적용됩니다. 그 전까지 오토파일럿에는 줄 수 한도가 없고 파일 수는 이미 1개로 제한되어 있습니다.
- 줄 수는 크기의 대용치일 뿐 위험의 크기와 같지 않습니다. 작은 변경도 위험할 수 있고, 그 판단은 CI·Audit·릴리스 봇의 몫으로 남습니다.
