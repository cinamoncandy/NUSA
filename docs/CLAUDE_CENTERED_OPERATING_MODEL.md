# NUSA Claude 중심 운영 모델 (전체 재설계 제안)

상태: **제안(PROPOSED)**. 이 문서는 아무것도 바꾸지 않습니다(`authority_impact: none`). 소유자가 §9의 결정을 내린 뒤 단계별(§8) 작업지시서로 나눠 진행합니다.
결정 기록: `.aipos/decisions/ADR-OPS-20261013-CLAUDE-CENTERED-OPERATING-MODEL.md`. 사실은 2026-10-12~13 저장소와 GitHub에서 확인한 범위이며, 다음 세션은 다시 확인해야 합니다(No-Guess Rule).

## 1. 왜 재설계하나
지금까지 개발 엔진·리뷰·자동 코딩의 중심은 ChatGPT/Codex였습니다. 소유자는 앞으로 **Claude를 중심으로** 운영합니다.
바꾸지 않는 것부터 분명히 합니다. 이번 재설계는 **누가 일을 하고 누가 검증하는지**를 다시 나누는 것이지, 안전 경계나 권한을 바꾸는 것이 아닙니다.

**절대 바뀌지 않는 것**
- PAPER_ONLY, `liveAuthority=NONE`, `productionMutationAllowed=false`, `aiAuthority=ZERO_AUTHORITY`. 자본·위험·임계값 완화 금지(연속 손실 한도 3 유지).
- "규칙이 결정하고 AI는 고친다": 분류·권한·재시도 예산·병합은 결정적 규칙이 정하고, AI는 허락된 범위의 수리만 합니다.
- 독립 Audit와 릴리스 봇(`nusa-release-authority`)만 병합합니다. 작성자는 자기 PR을 승인·병합하지 않습니다.
- AIPOS는 특정 AI에 묶이지 않습니다(`AGENTS.md`, `.aipos/AI_HANDOFF_CONTRACT.md`). `CLAUDE.md`는 그것을 가리키기만 합니다.

## 3. 목표 역할 (Claude 중심)
| 역할 | 누가 | 하는 일 | 하지 않는 일 |
|---|---|---|---|
| 소유자 | 사람 | 방향·우선순위·결정, 외부 설정(보호 규칙, 계정, DNS, 배포 승인) | 일상 구현 |
| **메인 Claude** | 소유자의 메인 Claude 계정(소유자와 함께 작업) | 설계와 중·대형 구현, 재설계 같은 큰 변경 | 자기 PR 승인·병합 |
| **보조 Claude** | 이 세션 계정 | 검증·운영 점검·연구·AIPOS 기록·소형 작업, **메인 PR의 독립 리뷰** | 메인과 같은 PR 동시 수정, 승격·병합 |
| **오토파일럿** | Worker + 결정적 제어부 + 제한된 AI 수리 | 허용된 실패의 소형 수리(150줄·1파일), 영수증 기록 | 소유자 코딩 중 새 작업 시작(게이트), 자기 엔진 실패 수리 |
| 독립 Audit | 결정적 Audit + 작성자가 아닌 리뷰어 | 정확한 head의 판정 | 구현 |
| 릴리스 봇 | `nusa-release-authority` | 병합·릴리스 판정 | 판단 우회 |

**독립성 규칙**: 작성자와 리뷰어는 **다른 세션·다른 GitHub 계정**이어야 합니다. 메인이 쓴 PR은 보조가, 보조가 쓴 PR은 메인 또는 결정적 Audit가 봅니다. 같은 계정의 같은 세션은 서로를 대신하지 않습니다.

## 4. 신원 분리 (선행 조건)
- GitHub 계정을 **메인 쪽**과 **보조·자동화 쪽**으로 나눕니다(소유자 2026-10-13 진행 예정). 오토파일럿 Worker 토큰, 자동화 러너, 보조 세션은 메인 쪽 계정을 쓰지 않습니다.
- 소유자 활동 게이트(#2644, 꺼진 채 배포)는 **분리가 확인된 뒤에만** 켭니다. 감시 대상은 메인 쪽 로그인입니다.
- 각 PR과 커밋에 남는 이름으로 누가 했는지 구별되게 합니다. 지금은 모든 PR이 `cinamoncandy`로 보여 구별되지 않습니다.

## 5. 작업 흐름
1. **작업 선택**: AIPOS `state.yaml`의 열린 작업과 소유자 우선순위. 한 작업 = 한 브랜치 = 한 PR.
2. **충돌 방지(신규)**: 작업을 시작하는 쪽이 `state.yaml`의 해당 항목에 `claimed_by: main|assistant|autopilot`과 시각을 남기고, 다른 쪽은 그 작업을 건드리지 않습니다. 오늘처럼 두 엔진이 같은 일을 겹쳐 PR을 만드는 일(#2585와 #2596)을 막습니다.
3. **크기 배분**: 150줄·1파일 이하이고 허용된 실패 수리 → 오토파일럿. 그보다 크거나 설계가 필요한 일 → 메인. 검증·조사·기록·소형 수정 → 보조.
4. **검증**: 로컬 검증 → 정확한 head의 CI → 독립 리뷰(§3 독립성 규칙) → 결정적 Audit → 릴리스 봇 병합.
5. **기록**: 각 단계의 결과를 AIPOS(작업지시서, `state.yaml`, 필요하면 인수인계)에 남깁니다. 대화는 증거가 아닙니다.

## 6. 오토파일럿 재설계 핵심
- **엔진**: 기본은 Workers AI(무료)를 유지합니다. Claude를 오토파일럿 엔진으로 쓰는 것은 **비용이 드는 결정**이라 소유자 승인 전에는 하지 않습니다(§9-3). 메인·보조 Claude는 소유자의 구독 세션으로 일하고, 저장소 안의 자동 실행에 Claude API 키를 넣지 않습니다.
- **자기 실패 재시도 금지(신규, 필수)**: 오토파일럿이 자기 엔진 워크플로(Codex 코딩 등)의 실패를 수리 대상으로 다시 보내지 않게 합니다. 한 실패 실행당 수리 요청은 1회로 묶습니다. 오늘의 5분 주기 알림 폭주의 원인입니다.
- **소유자 활동 게이트**(#2641 설계, #2644 구현): 메인 쪽 계정이 60분 조용할 때만 새 작업을 시작하고, `/autopilot pause <1~24>h` 수동 보류를 지원합니다.
- **크기 한도**: 150줄(적용 중), 파일 1개(기존 규칙).
- **완료 영수증**(설계 병합, #2637~#2639 보류 중): 실제 코드 실패 한 건이 패치→PR→CI→독립 Audit→병합까지 가야 `AUTOPILOT_VERIFIED_COMPLETION_LOOP=true`.

## 7. 리뷰와 알림
- **리뷰 교체**: 한도에 걸린 Codex 리뷰 봇 대신, **작성자가 아닌 Claude 세션**이 리뷰합니다(예: 보조가 메인 PR에 `/code-review`). 리뷰 결과는 PR 댓글로 남기고, 지적은 작성자가 고칩니다. 리뷰는 판정이 아니며 결정적 Audit를 대신하지 않습니다.
- **알림 줄이기**: (1) 자기 실패 재시도 금지, (2) 같은 실패에 대한 반복 실행 묶기, (3) 보조 세션은 조치가 필요할 때만 짧게 보고합니다.

## 8. 이전 단계 (각 단계는 별도 작업지시서, 되돌릴 수 있게)
| 단계 | 내용 | 끝났다는 증거 |
|---|---|---|
| P0 | 신원 분리, 브랜치 보호 재확인, 이 문서 승인 | 두 로그인 확인, 보호 규칙 확인 |
| P1 | 오토파일럿 자기 실패 재시도 금지, 작업 `claimed_by` 규칙 | 테스트, 같은 실패에 반복 실행 없음 |
| P2 | 보류 PR 정리: 영수증 묶음(#2637~#2639) 병합 진행, 설계 문서(#2641, #2642) 병합, 게이트(#2644) 병합 후 분리 확인되면 켜기 | 병합 기록, 게이트 닫힘/열림 확인 |
| P3 | 리뷰 교체(작성자가 아닌 Claude 리뷰를 표준 절차로) | PR마다 독립 리뷰 기록 |
| P4 | 엔진 결정(Workers AI 유지 또는 Claude 엔진, 비용 승인 필요) | 소유자 결정 기록 |
| P5 | Codex 자산 정리: `Autopilot Codex Coding`·`Oracle Codex Dev Runner`·Codex 리뷰 설정을 보관 또는 제거(소유자 결정) | 워크플로 상태, 문서 갱신 |

## 9. 소유자 결정 항목
1. 이 역할 표(§3)와 독립성 규칙을 채택하는가.
2. 두 GitHub 로그인(메인 쪽, 보조·자동화 쪽).
3. 오토파일럿 엔진: Workers AI 유지(무료, 권장) 또는 Claude 엔진(유료, 상한 필요).
4. Codex 자산(코딩 워크플로, 호스트 러너, 리뷰 봇)을 보관할지 제거할지.
5. 보류 PR 처리 순서(§8 P2 권장안 수용 여부).
6. 연구: 장세 신호 변형을 사전 등록해 앞으로의 데이터로 평가할지(현재 중단).

## 10. 한계
- 제안 문서이며 아직 아무것도 바뀌지 않았습니다. 일부 사실(외부 서비스 설정, 계정 연결, 보호 규칙)은 이 세션에서 직접 확인할 수 없습니다.
- 학습 폐루프(0/7)의 원인은 운영 모델이 아니라 Research 심사를 통과한 후보가 없다는 점입니다. 이 재설계만으로 학습이 돌지는 않습니다.
