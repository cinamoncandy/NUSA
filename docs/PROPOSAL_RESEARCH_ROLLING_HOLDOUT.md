# 제안: 과거 데이터를 여러 개의 독립 홀드아웃으로 나눠 평가 (제안만, 구현 전)

Safety stays: PAPER_ONLY, liveAuthority=NONE, productionMutationAllowed=false. 연구 증거만 만든다. 주문·자본·위험·실행 설정은 바꾸지 않는다.
상태: **소유자 승인 전. 이 문서는 어떤 동작도 바꾸지 않는다.**

## 왜
지금 연구는 가장 최근 구간 하나(훈련 7일 / 검증 2일 / 홀드아웃 2일)만 평가한다 (`researchWalkForwardWindows.ts`, 최근 한 세트만 만든다).
홀드아웃 하나는 우연히 통과하거나 우연히 탈락하기 쉽다. 과거 캔들은 시작할 때 업비트 공개 API로 채워지므로(`researchCandleBackfill.ts`),
기다리지 않고 **서로 겹치지 않는 여러 홀드아웃**으로 같은 후보를 더 일찍, 더 단단하게 판정할 수 있다.

## 안 바꾸는 것
- 기존 통과 규칙, 임계값, 일일 예산, 사전 등록(precommit) 절차: 그대로.
- 홀드아웃은 후보 선택에 쓰지 않는다. 후보는 평가 전에 고정(사전 등록)된다.
- 합성·보간 캔들 금지. 결측률 한도(`maxMissingRatio`) 그대로.

## 설계
1. 이력을 시간순으로 겹치지 않는 N개의 (훈련→검증→홀드아웃) 접힘(fold)으로 나눈다. 각 접힘은 자기보다 앞선 데이터만 쓴다(미래 정보 금지).
2. 후보는 접힘별로 **한 번만** 평가한다. 같은 접힘을 후보 선택에 재사용하지 않는다.
3. 통과 조건은 **더 엄격하게만**: N개 중 최소 K개 접힘의 홀드아웃을 통과(예: 3 중 2). 단일 홀드아웃 통과는 더 이상 충분하지 않다.
4. 다중 비교 보정: 접힘 수 × 후보 수가 늘어나므로 일일 예산 상한은 유지하고, 통과 K는 접힘 수에 맞춰 사전 등록한다.
5. 결과는 접힘별 코드와 정수(통과 수/전체 수)로만 /health에 낸다(표시 전용).

## 위험과 막는 방법
- 같은 이력을 여러 후보가 반복 사용하면 홀드아웃이 "소모"된다 → 후보당 접힘 평가 1회, 사전 등록 이후 변경 금지.
- 접힘이 짧으면 표본이 부족하다 → 접힘별 최소 거래 수·최소 캔들 수 미달이면 `INSUFFICIENT_EVIDENCE` (통과로 세지 않음).
- 구현이 기준을 느슨하게 만드는 버그 → K-of-N은 단일 홀드아웃보다 언제나 엄격함을 테스트로 고정.

## 소유자에게 필요한 결정
1. N(접힘 수)과 K(통과 수): 제안 N=3, K=2.
2. 각 접힘 길이: 기본 7/2/2일 유지 시 12일 × 3 = 최소 약 22일 이력(접힘이 일부 겹치지 않게 시간순 배치). 이력 길이 `NUSA_RESEARCH_TRAIN_DAYS` 조정 필요 여부.
3. 적용 범위: 1m/15m/60m 모두 vs 일부.

## 검증 계획 (구현 시)
- 접힘이 겹치지 않고 시간순이며 미래 데이터를 쓰지 않는지 속성 테스트.
- K-of-N이 단일 홀드아웃보다 통과를 늘리지 않는지(엄격성) 테스트.
- 결측·표본 부족 시 통과로 세지 않는지.
- 서버에서는 배포 후 /health의 접힘별 통과 수 확인.

## 아직 확인하지 않은 것
- 실제 서버에 채워진 이력 길이, 기존 사전 등록 스키마가 접힘 단위를 담을 수 있는지(`researchProvenanceBuilder`, precommit store).
